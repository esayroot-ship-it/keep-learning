# Engineering Expansion

Use this reference when engineering/architecture is the selected practical goal, or one such concern is indispensable to the current normal-work task. Merely mentioning a product or asking to use it proficiently does not select every engineering discipline.

Basic error handling, input checks, transaction use or result verification needed for the chosen work remain core. Deeper implementations, uncommon failures, broad performance tuning and specialist architecture normally belong in a one-line extension direction. Expand only after an explicit request or a demonstrated core-task dependency, within the stated scope/time budget.

Keep the teaching-first order and select the matching training mode:

1. make the smallest example, model, operation, or system view understandable;
2. let the learner explain it and complete one mode-appropriate activity;
3. introduce one engineering concern;
4. show the smallest code, operation, or design change that addresses it;
5. verify the resulting behaviour or decision.

Possible concerns include errors, tests, configuration, logging, timeouts, retries, transactions, concurrency, performance, reliability, and observability. Select only concerns relevant to the current lesson. Do not automatically turn Redis, queues, databases, servers, or concurrency topics into a complete architecture curriculum.
